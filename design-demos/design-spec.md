# opencode2api WebUI 重设计共同 spec

## 项目理解

opencode2api 的 WebUI 不是营销页，而是给自托管服务操作者使用的管理控制台。用户通常在服务刚部署、请求异常、上游切换或需要调整配置时打开它；他们最关心的是「现在是否健康」「问题在哪里」「我改动了什么、是否已经生效」。因此重设计的核心不是增加内容，而是把当前已经存在的能力重新编排成一条更短、更安全、更可解释的操作主线。目标用户具有开发者或运维背景，但不应该被迫阅读源码才能知道一次保存的后果。

## 必须保留的能力与真实数据边界

所有方向都必须保留现有 API 与行为，不新增后端依赖：

- 登录、会话过期、退出登录，以及 CSRF 保护下的写操作。
- 运行总览：最近一小时请求总数、成功率、P95 延迟、活跃请求/流式数；Proxy 健康、Key 池状态，以及端点、状态码、模型、Tier 聚合。
- 配置中心：服务监听、优先 Tier、WebUI 开关与监听、Session TTL、Zen 匿名模式、Server/Zen/Go Keys、Proxy 与 Proxy File、Zen/Go 上游、重试、模型刷新与协议覆盖、连接池、超时、失败冷却、日志级别和 Ring Size。
- 配置保存时的验证、原子应用、需要重启的字段提示，以及从磁盘重载。
- 密钥与代理默认脱敏；通过二次验证查看完整值的模态流程。
- 实时 SSE 日志：级别、模块、全文检索、暂停/继续、事件流断档提示。
- 账号更新：当前密码校验、新账号、新密码，以及更新后重新登录。

初稿使用的是明确标注的「演示态」占位数据，不把假统计伪装成真实运营数据。生产版接入现有 API 后，所有数字、Proxy、Key、日志和重启字段都必须由接口返回；接口失败、无数据、断流、过期和权限不足要有可理解的状态，不用静默空白掩盖。

## 目标场景与主线 UX

主线有三条：第一条是「发现」——打开后 5 秒内判断服务是否可用，并能从总览跳到对应资源；第二条是「修复」——从异常状态进入配置或日志，完成修改后明确知道哪些字段即时生效、哪些要重启；第三条是「审计」——查看敏感配置和实时事件时，用户始终知道自己正在查看什么、是否会泄露、数据是否是实时的。导航应把「监控」「配置」「日志」「账号」作为四个清晰的工作空间，而不是把所有内容压缩进同一种卡片。

信息架构采用渐进披露：总览只展示决策所需的信号；配置按任务分组，常用项先露出，高风险/低频项折叠或分组；日志默认显示最新事件，筛选器和暂停状态常驻；账号安全与敏感值查看要用更强的视觉警示，但不使用恐吓式红色泛滥。每个提交动作都给出结果、影响范围和下一步，避免只弹一个「成功」。移动端不追求把桌面表单缩小，而是把桌面侧栏变成顶部工作区切换，保持 44px 触控目标与清楚的章节顺序。

## 共同视觉与可用性底线

- 正文不低于 14px，移动端优先 16px；中文正文行高约 1.7；表格数字使用等宽数字。
- 色彩用少量有意图的信号色：健康、警告、错误、重启待处理。大面积背景使用压低饱和度的中性色，不用通用紫色渐变、emoji 或装饰性图标堆砌。
- 通过规则线、留白、字重和版式建立层级，避免「圆角卡片 + 左侧彩条」的模板化 Dashboard 语言。
- 交互结果尽量在原地解释：保存、重载、二次验证、暂停日志、会话失效都要有可定位的反馈；错误信息保留后端真实消息。
- 三个方向都提供真实可点击的原型交互：工作区切换、配置展开、日志暂停、敏感值查看抽屉/模态、危险操作确认等；这些交互是原型状态，不会伪装成已接通 API。

## 三个方向的差异化命题

1. **Signal Room / 信号室**：深色运行台，先看服务脉搏，再按异常进入资源抽屉。适合高频值守与快速定位。
2. **Field Manual / 运维手册**：暖白出版物式的结构化控制台，用规则线和章节编号把配置变成可阅读的操作手册。适合重视稳定、审计和长时间阅读的用户。
3. **Command Atlas / 命令图谱**：黑底技术地图，把路由、上游、Key、Proxy 和日志组织成一张可追踪的系统图。适合喜欢命令行/基础设施语境、希望理解请求路径的用户。

## 输出与验证

三版原型统一以 1440×900 桌面首屏为比较基准，同时考虑 390px 移动宽度。每版都保存为独立 HTML，能够离线打开；生产接入时保留现有 endpoint，不改变后端字段。初稿完成后用 Playwright 检查桌面与移动截图、控制台错误、主要点击路径，再等待用户选择一个方向或提出混合方案。用户未选择前不创建实现 gate 文件 `direction-approved.md`，也不修改 `webui/index.html`。
